# ADR 56: The maintainer-only generators stay exempt from the C-and-mino rule for now

Date: 2026-09-06

## Context

The project rule is that tooling is written in C or in mino, so a
contributor needs no third runtime to work on the language. Two tool
families under `tools/` break that rule today:

- `gen_arglists.clj` runs on JVM Clojure or Babashka (`clojure.java.shell`,
  `System/getProperty`), not the mino dialect. It regenerates the committed
  `src/prim/arglists_data.h` install-time arglist table from the census
  oracle surface.
- Seven Python generators (`gen_html_oracle.py`, `gen_xml_oracle.py`,
  `gen_zip_oracle.py`, `transcribe_html5lib.py`, `gen_html_entities.py`,
  `gen_zip_cp437.py`, `gen_unicode_case.py`) transcribe upstream reference
  data (the WHATWG entity table, html5lib and zip oracle corpora, the Unicode
  case-folding tables, CP437) into committed C headers and EDN test fixtures.

Every one of them is a maintainer-only regeneration step whose output is
committed to the tree. None sits on the `make` or `./mino task build` path an
embedder or a from-source builder runs; only `gen_unicode_case.py` is wired to
a task, and that task is a maintainer regeneration, not a build. The mino-side
tools in the same directory (`bump_satellites.clj`, `flatten_branch.clj`,
`gen_coverage_manifest.clj`) already run under `./mino` and are not at issue.

## Decision

The JVM-Clojure and Python generators stay as they are for now, exempt from
the C-and-mino rule, and this phase does not migrate them. The physical-motion
phase moves files; a tool rewrite is behavior-bearing work with its own test
surface (the regenerated bytes must stay identical), so it does not belong in
an inert motion pass. The exemption is scoped and named here so the debt is
visible rather than silent: the rule holds for anything on the build path and
for any new tool, and these named generators are the grandfathered exception
until a migration cycle retires them.

## Consequences

A maintainer regenerating arglists or a reference-data header still needs a
JVM/Babashka or a Python 3 on the path, which the `doctor` task does not yet
report. The generated outputs are committed, so a plain contributor who only
edits code and runs the suite needs neither runtime; the dependency bites only
the maintainer who regenerates. The debt is bounded: each generator is a
pure transcription with a byte-stable output that a future mino rewrite can be
checked against by diffing the regenerated file.

## Alternatives

**Rewrite the generators in mino now.** Ends the third-runtime dependency and
satisfies the rule immediately. Rejected for this phase: it is a
behavior-bearing rewrite with a real correctness gate (byte-identical
regeneration of oracle corpora and Unicode tables), which is the opposite of a
semantically inert file-motion pass. It earns its own cycle.

**Delete the generators and freeze the committed outputs.** Removes the
dependency by removing the tools. Rejected: the outputs must be regenerable
when upstream reference data moves (a new Unicode version, a WHATWG entity
update); freezing the tables would strand them at today's upstream and hide the
provenance the generators document.
